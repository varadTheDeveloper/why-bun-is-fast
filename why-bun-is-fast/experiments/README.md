# Experiments

Six controlled experiments, each testing one specific, source-motivated mechanism rather than producing a single blanket "Bun vs. Node vs. Deno" number. See [`methodology/`](../methodology/) for the shared methodology across all six, and the [article](../article/why-bun-is-fast.md) for how each experiment's result fits into the overall investigation.

| Experiment | Question | Result |
|---|---|---|
| [H1](h1-native-call-boundary/) | Does the native binding path (not just the JS engine) affect per-call overhead crossing from JavaScript into native code? | Bun's own `bun:ffi` path was fastest of all tested paths, but the *identical compiled native addon*, run through Bun's N-API compatibility layer instead of its own preferred mechanism, was ~3.7× slower than the same addon run through Node's native N-API. Binding-path implementation, not engine identity alone, drove the result. |
| [H2](h2-fetch-thread-hop/) | Does Bun's dedicated background thread for `fetch()` create a measurable latency penalty relative to Node's and Deno's single-threaded event loop approach? | No net penalty detected in aggregate — Bun was fastest in both cold-connection and keep-alive conditions, despite paying for the extra thread hop that neither Node nor Deno incurs for this call. |
| [H3](h3-coldstart-page-faults/) | Does Bun's documented cold-start binary layout (`#[cold]`-tagged code kept off the hot startup path) produce fewer page faults, and does that translate to faster startup? | Bun had far fewer total page faults than Node or Deno. Cold startup *time* was statistically tied with Deno despite Deno having more total faults — fewer page faults did not translate into a faster measured start. |
| [H4](h4-http-sync-async/) | Does the header/URL copy Bun's server performs when a request handler suspends (rather than responding synchronously) show up as a measurable throughput cost? | A synchronous handler was ~10.5% faster than a genuinely-suspending async handler at concurrency 1. At concurrency 50, the effect reversed — the async path was very slightly ahead. |
| [H5](h5-buffer-pool/) | Does Node's `Buffer.allocUnsafe()` pooling (which Bun's implementation does not replicate) produce a measurable allocation-throughput advantage, and is the effect threshold-dependent? | Node's pool wins below a measured 4,096-byte threshold (by 8% to just over 22%); Bun wins at and above it (by just over 200% to nearly 290%) — the winner flips exactly where the source-level mechanism predicts it should. |
| [H6](h6-realistic-io-convergence/) | Does adding a realistic database call change which runtime wins an HTTP benchmark, and does the runtime gap shrink toward convergence under that more realistic load, as some external benchmarks have reported? | The ranking fully inverted: Deno led on a plaintext workload, Bun led once a single database call was added. The overall fastest/slowest gap narrowed by roughly 8% — real, but well short of the "substantial convergence" some external, independently published benchmarks have reported under different (heavier) realistic workloads. |
| [H7](h7-startup-cache-config/) | Does Bun's default-on startup cache produce a measurable advantage over Node's opt-in equivalent, isolated from the general startup-cost story already covered by H3? | **Deferred — not executed.** See that folder's README for the full reasoning. |

## What this table intentionally does not say

None of these results generalize into a single "Bun is fast because X" statement — that is the article's central finding, not an oversight of this index. Each result above is scoped to the specific condition it was measured under (a buffer size range, a concurrency level, a workload type), and each experiment's own README documents the counter-evidence and limitations that keep its result from being overstated. See the article's §11 ("Where Bun doesn't win") and §12 ("What we still don't know") for the full, deliberately preserved list of counter-evidence and open questions.
